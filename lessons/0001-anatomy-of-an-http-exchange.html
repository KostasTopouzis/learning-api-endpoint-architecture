Lesson 01 · Foundations

The anatomy of an HTTP exchange

Every endpoint you will ever build reads one message and writes one message back.

When you added a Vercel Function to Marquee Moon, you wrote code that “handles a request”. This lesson makes that request visible: what it physically is, which parts it has, and where each part shows up in your TypeScript. Time: about 15 minutes. You need a terminal and Chrome.

The one idea HTTP is a conversation of two text messages. The client always speaks first with a request; the server answers with a response. An endpoint is a function from the first message to the second. MDN: the client “is always the entity initiating the request. It is never the server.” — Overview of HTTP

Both messages share the same four-part shape: Structure from MDN: HTTP messages. The start line plus headers together are called the head.

  1. A start line: what is being asked for (request), or how it went (response).
  2. Headers: one Name: value pair per line, describing the message.
  3. An empty line: “the head is over”.
  4. A body (optional): the actual data, like JSON or HTML.

A real request, to TMDB

This is the exact request curl sent when I asked TMDB for movie 603 (The Matrix) today, with no API key. Click each coloured part.

Notice what is not there: no body. A GET asks for something, so it has nothing to send. POST, PUT and PATCH are the methods that carry a request body. “Only PATCH, POST, and PUT requests have a body.” — MDN

TMDB's response

The response's start line is called the status line; the request's is the request line. That 401 is not a bug: it is TMDB telling us, in a precise format, that we didn't authenticate. Hold that thought. Where your TMDB key lives is the subject of an upcoming lesson. Status codes come in five classes: 1xx informational, 2xx success, 3xx redirection, 4xx client error, 5xx server error. — MDN: status codes

Two more facts to carry with you:

  • HTTP is stateless. The server keeps no link between two requests. Anything it needs to know, such as “this is that shopper's cart”, must ride along inside each request, usually as a header (a cookie or a token). “Stateless, but not sessionless”: cookies add sessions on top, via headers. — MDN
  • HTTP/2 and HTTP/3 change the packaging, not the parts. They send binary frames instead of text, and the start line becomes “pseudo-headers” (:method, :path, :status). The method, path, status, headers and body are all still there. “The semantics are the same.” — MDN: HTTP/2 messages

The same parts, in your code

A Vercel Function receives the request message as a standard Web Request object and returns a Response object. The platform does the parsing and the writing. You only read and set the parts. Function signature from Vercel Functions docs. The Edit's Next.js Route Handlers (export async function GET(request: Request)) use the very same objects: Next.js docs. 

// api/movie.ts  — a Vercel Function in Marquee Moon
export default {
  async fetch(request: Request) {
    // ── read the REQUEST message ─────────────────────────────
    request.method;                    // "GET"          ← request line
    new URL(request.url).pathname;     // "/api/movie"   ← request line
    request.headers.get("accept");     // "*/*"          ← a header
    // await request.json();           // the body (POST / PUT / PATCH)

    // ── write the RESPONSE message ───────────────────────────
    return new Response(
      JSON.stringify({ title: "The Matrix" }),             // ← body
      {
        status: 200,                                       // ← status line
        headers: { "Content-Type": "application/json" },   // ← headers
      },
    );
  },
};

You never write the empty line or the protocol version: the runtime serialises your Response into a real message. That's the whole trick. Once you can see the two messages, “building an endpoint” means deciding which request it accepts and which response it returns. Every later lesson (methods, status codes, errors, auth, caching) is a decision about one of these parts.

Practice 2 · Recall

No scrolling up. Retrieval is the point: a wrong answer now makes the right one stick.

In an HTTP/1.1 message, where does the empty line go?

  • Before the start line, opening it
  • Between the start line and headers
  • Between the headers and the body
  • After the body, closing the message
The empty line marks the end of the head (start line + headers). Everything after it is the body.

Your function for The Edit replies 201 Created. Which part of the response carries the 201?

  • The status line
  • A response header
  • The response body
  • The request line
The status line is <version> <status code> <reason phrase>, e.g. HTTP/1.1 201 Created.

In GET /api/movies/603 HTTP/1.1, what is /api/movies/603?

  • The method to perform
  • The target resource path
  • The protocol version used
  • The server's host name
It's the request target: which resource. The domain travels separately, in the Host header.

Which header tells the receiver how to interpret the bytes in the body?

  • Host
  • Accept
  • Content-Length
  • Content-Type
Content-Type describes the body's format (e.g. application/json). Accept is what the client would like back; Content-Length is only the size.

HTTP is stateless. What does that mean for The Edit's shopping cart?

  • The server remembers every cart between requests
  • Each request must carry its own context
  • Carts only survive within a single connection
  • Carts live inside the response status line
The server keeps no link between requests, so each one must identify the shopper itself, typically with a cookie or token header.

In a Vercel Function, which piece of code decides the response's status line?

  • The request.method value
  • The Content-Type header
  • The status option
  • The JSON.stringify call
new Response(body, { status: 201 }) → the runtime writes HTTP/1.1 201 Created.

Practice 3 · See it in the wild

  1. In PowerShell, run: 
    curl.exe -i https://api.themoviedb.org/3/movie/603
    -i prints the response head as well as the body. You should get the same 401 as above. Name its four parts out loud. Use curl.exe, not curl, so PowerShell can't swap in a different command.
  2. Now run it with -v instead of -i. Lines starting > are the request curl sent; lines starting < are the response. Find the request's empty line.
  3. Open Marquee Moon in Chrome, press F12 → Network → filter Fetch/XHR, then reload. Click a request to TMDB and find: the method, the status code, the response Content-Type, and the body (Preview tab). If the Protocol column says h2 or h3, the message travelled as binary frames. Same parts. Guide: Chrome DevTools: Network.
  4. Bring back one observation: in that request, where does your TMDB API key appear: in the URL, in a header, or nowhere? Who else could see it? Tell me your answer next session.
